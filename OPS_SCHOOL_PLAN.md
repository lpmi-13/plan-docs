# Ops School contribution plan

## Assessment as of 28 September 2026

The strongest contribution opportunity is now a **short, practical web-service learning path**. [Ops School's labs page](https://www.opsschool.org/labs.html) lists “Install Apache,” “Configure a virtual host,” and “Display a simple web page,” but gives learners no environment, diagnostic variants, success checks, or reset procedure. Its [HTTP 101](https://www.opsschool.org/http_101.html) already explains requests, responses, listeners, and virtual hosts, so the missing work is chiefly *guided application and assessment*, rather than another general HTTP explanation. The [systemd section](https://www.opsschool.org/inits.html) is empty, and [Troubleshooting](https://www.opsschool.org/troubleshooting_101.html) leaves several failures as prompts. Ops School's [contribution guidance](https://www.opsschool.org/meta/contributions.html) encourages interactive work for learners approaching junior sysadmin level.

The [knowledge-graph PoC](/home/adam/projects/knowledge-graph-poc/README.md) makes that opportunity more concrete than the plans in this directory alone. Its first outcome is to deploy a static site on one VM, verify it from a second VM, and diagnose failures. This **changes the recommended first coordinated contribution** from three unrelated one-VM exercises to a connected, two-VM sequence. An idempotent automation example remains the smallest *independent* documentation contribution.

**Editorial fit:** Ops School's existing HTTP lab names *Apache*, while the PoC uses *Nginx*. Its HTTP chapter already discusses both. Present the Nginx path as an alternative web-server exercise or agree on a broader lab heading with maintainers; do not silently turn the Apache task into an Nginx task. The core outcomes—listener, virtual host, response, and remote verification—remain useful with either server.

## Small contributions outside the first web-service path

- **Idempotent configuration and convergence:** [Configuration Management 101](https://www.opsschool.org/config_management.html) explicitly asks for a concrete example. A one-VM script that is run twice, followed by induced drift and repair, is still the **easiest standalone contribution**. The [Linux Mastery plan](LINUX_MASTERY_SYSTEM_PLAN.md) supplies a practice pattern. Keep this separate from HTTP request retry semantics.
- **System metrics:** [Looking at system metrics](https://www.opsschool.org/stats_diagnosing.html) has tool headings but little diagnosis. A one-VM CPU-versus-I/O exercise can use the baseline/fault/ground-truth pattern in [BPF Exploration](BPF_EXPLORATION_PLAN.md). Check [existing PR #352](https://github.com/opsschool/curriculum/pull/352), which proposes material on `stat`, `vmstat`, and `strace`, before duplicating command explanations.
- **Retries and duplicate effects:** [Architecture 201](https://www.opsschool.org/architecture_201.html), [Application Components 201](https://www.opsschool.org/application_components_201.html), and [Databases 201](https://www.opsschool.org/databases_201.html) leave room for a reliability lesson. The [Django idempotency plan](IDEMPOTENCY_DEDUPLICATION_DJANGO_LAB_PLAN.md) is a strong outline, but a reliable app/Postgres lab is more work than the web-service path.
- **Tracing and cloud incidents:** [BPF Exploration](BPF_EXPLORATION_PLAN.md) and [AUUS](AUUS_SIM_PLAN.md) offer advanced scenarios. A narrow tracing comparison or SQS poison-message story could become later material. Their full tooling and simulator plans are large projects and are not prerequisites for these first lessons.

[Lab Visualization](LAB_VISUALIZATION_PLAN.md) and [Frontend Performance](FRONTEND_PERF_VIZ.md) are mainly potential teaching tools or adjacent topics. The scavenger-hunt plan offers a concurrency example; the voice and physical-blocks plans have little direct Ops School fit.

## What a publishable lesson and working lab still need

1. **Write the learner-facing material.** For each exercise, state prerequisites, the initial situation, one observable goal, a short conceptual explanation, optional hints, expected evidence, and a reset path. Ops School uses reStructuredText and asks contributors to build the documentation and check links. [Contribution instructions](https://github.com/opsschool/curriculum)
2. **Make the VM state reproducible.** Launch the draft [two-VM manifest](/home/adam/projects/knowledge-graph-poc/playgrounds/two-vm-web.yaml), record or pin its image/setup versions, and add separate setup for each variant. Verify the intended failure before a learner begins. A failed setup is a lab error, not a learner failure. Use a **fresh play** for a new attempt; restarting a stopped play does not provide a clean reset. [iximiuz playground documentation](https://labs.iximiuz.com/docs/playgrounds/how-to-use-playgrounds)
3. **Check behavior and diagnosis separately.** Test the resulting site from `client-01` using the expected status and a unique body marker. For diagnostic skills, collect the learner's cause and supporting observations before hints. Accept alternative safe repairs; do not grade command history. The [matrix](/home/adam/projects/knowledge-graph-poc/SKILL_ASSESSMENT_MATRIX.md) and [blueprints](/home/adam/projects/knowledge-graph-poc/ACTIVITY_BLUEPRINTS.md) specify these distinctions.
4. **Calibrate each grader.** Run it against the untouched fault, an intended solution, a plausible wrong repair, and a different valid repair. The wrong states must fail, and both valid repairs must pass. Then try the exercise with a few learners and revise confusing prerequisites, wording, and checks.
5. **Choose the lightest useful publication path.** A written Ops School exercise can be contributed before automation. An iximiuz [Tutorial](https://labs.iximiuz.com/docs/learning-materials/tutorials) or [Challenge](https://labs.iximiuz.com/docs/learning-materials/challenges) can supply a playground and task checks. Current [authoring guidance](https://labs.iximiuz.com/courses/labs-docs/content-authoring/how-to-publish-content) says original published content requires a Premium or Tinkerer account. Use an existing challenge or a shared playground link if publishing access is unavailable. The PoC's external controller is useful when per-skill evidence and progress matter, but it need not precede an Ops School lesson.

## Recommended first package

Prepare **one Ops School exercise and one verified two-VM playground** for the clean-deploy task. This proves the written format, current Ubuntu/Nginx commands, cross-VM access, marker check, and fresh reset. Follow with the failed-unit and loopback-bind variants using the same base environment. Keep the [19-node graph](/home/adam/projects/knowledge-graph-poc/devops-skills-kg-poc/graph.json) as a versioned authoring and assessment map; review its proposed edges with operators and learners before using them to block progress.

This sequence contributes usable teaching material quickly while making the knowledge-graph PoC testable. It leaves the adaptive mastery system, cloud simulator, and visualization products as later work.
