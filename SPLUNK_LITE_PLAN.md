# Remote Detection Lab: iximiuz Labs playground plan

## Decision and intended outcome

Build a **standalone, short-lived iximiuz Labs playground** that teaches the useful parts of an instrumented attack range: observe real events, trace them through a collection pipeline, investigate them, write a detection, and test the detection against benign and suspicious activity. The public title and UI should use **Remote Detection Lab** (or another neutral name); no Splunk name, logos, binaries, licenses, or default passwords are needed.

This is a new learning environment inspired by the outcomes of the `attack_range` repository, not a fourth backend for that application's Terraform/API workflow. Learners start their own playground from the iximiuz page or `labctl`, use its browser terminals or `labctl ssh`, and discard the instance when finished. There is no VPN, cloud account, Terraform state, Ansible controller, public router, or separate control-plane service.

**MVP:** two Linux VMs on one private playground network, a small local web application, real Linux and application logs, a lightweight open-source log pipeline, and four guided exercises. Make the first release work within the documented free-tier budget if a cold-start test confirms it; otherwise state the required tier plainly. Publish only after the platform and safety gates below pass.

## What learners will actually learn

| Learning outcome from a conventional attack range | Safe, hands-on replacement | Evidence the learner produces |
| --- | --- | --- |
| Build and inspect an instrumented target | Inspect a prebuilt target VM, its `systemd` units, local socket list, app config, and log sources | A diagram or short explanation of where an event originates and how it reaches the search UI |
| Generate technique-linked telemetry | Run bounded, author-written actions against seeded files and the lab's own app | Timestamped events with the expected VM, service, and action fields |
| Hunt across multiple evidence sources | Query actual journald/app logs; optionally inspect a bounded capture on the private VM interface | A timeline and at least one corroborating source |
| Develop and validate a detection | Write a LogQL query and, if the UI supports it, a dashboard or alert rule; replay positive and negative cases | A query, an expected match, and a stated false-positive limitation |
| Export/share findings | Save the query and a short Markdown case note in the VM, or copy them out using the user's own browser/SSH session | A portable rule and explanation, with no retained production data |

The curriculum should distinguish **real system observations** from **synthetic fixture content**. The web application's HTTP and authentication events are real events generated by the learner's requests; any files used as discovery or collection targets are explicitly fictional. ATT&CK IDs may be shown as teaching references only when the exercise truly represents the named behavior, with the word *emulation* and the scoped target stated. Do not claim that reading a seeded file reproduces a full intrusion.

## Playground topology and access

Use a `flexbox` custom playground with two separate, pinned Linux rootfs images built from iximiuz's official bootable rootfs. `flexbox` is the documented base that permits an arbitrary machine set. An illustrative starting budget is **2 vCPU / 4 GiB** for `observe-01` and **1 vCPU / 2 GiB** for `target-01` (3 vCPU / 6 GiB total); measure the actual peak memory and cold-start time before locking this in. The platform currently documents free-tier caps of 2 vCPU / 4 GiB per VM and 5 vCPU / 8 GiB per playground. Requests above a cap can be scaled down, so the manifest alone does not prove a lab will fit.

| VM | Services and data | Learner access |
| --- | --- | --- |
| `observe-01` | Single-binary Loki with local filesystem storage, Grafana with a preconfigured Loki datasource, bounded retention, an example dashboard, and a local exercise checker | Browser terminal; Grafana `http-port` tab; `labctl ssh` |
| `target-01` | Small author-written HTTP app with seeded fake accounts and documents; `systemd-journald`; Grafana Alloy reading only the selected service/journal sources and pushing to `observe-01`; optional auditd after validation | Browser terminal; `labctl ssh` |

Create one bridge network such as `10.77.0.0/24`, set `private: true`, and use stable addresses (`10.77.0.10` and `.11`) in collector and fixture configuration. In the documented manifest, `private: true` means no Internet NAT or default route via that network. Both VMs should have **only this private interface** in the published manifest. Listen on the VM's main interface where an iximiuz `http-port` tab requires it; keep Loki's API accessible only inside the playground and expose only the Grafana UI through the platform tab. Do not call `labctl expose port` or make a public terminal session part of the default flow. Verify in a real instance that browser terminals, `labctl ssh`, and the Grafana tab still work on private-only VMs; this is a release gate, not an assumption.

### Data-flow boundary

**No playground guest should send telemetry or contact a service on the public Internet.** The intended guest traffic is limited to loopback and the two VMs' private addresses: `target-01` Alloy pushes logs to `observe-01` Loki; Grafana queries that Loki; the learner and scenario scripts contact only the known lab app address; and local checkers read local files or query these private services. No hosted SIEM, Grafana Cloud, public webhook, remote-write/OTLP exporter, external DNS lookup, package mirror, license lookup, analytics endpoint, or public test target belongs in the guest configuration or exercise instructions. Use static lab IPs where possible to avoid a dependency on external name resolution.

There are unavoidable **platform access paths** to distinguish from guest egress: the learner's browser or `labctl` connects to iximiuz to start and access the playground, the browser's Grafana tab may be proxied by iximiuz, and iximiuz may fetch the OCI rootfs from the author's public registry before guest boot. Those paths may carry control-plane data or viewed log data through the platform even when the guest network is private. Confirm the actual proxy and image-pull behavior with iximiuz; do not claim that *all* bytes remain inside `10.77.0.0/24`. The release requirement is that our guest services and exercises make **no outbound public-Internet connections**, and that any platform-mediated access is understood and accepted.

Start with `accessControl.canList`, `canRead`, and `canStart` set to `owner` for private testing. For publication, choose the intended learner audience in iximiuz access control; each learner must start an isolated instance of the template rather than sharing the author's running VM. Keep the Grafana tab private to that learner; do not enable a public HTTP URL or shared terminal session. The published playground should be **ephemeral**: its documentation tells learners to use `labctl playground destroy <play-id>` or the UI Destroy action, rather than Stop, which preserves disks. Natural expiry also destroys ephemeral plays according to the platform's documented lifecycle.

## Software packaging and boot

1. Build the two `linux/amd64` bootable OCI rootfs images from a pinned iximiuz rootfs base. Pin package/binary versions and publish the image by digest (`oci://ghcr.io/...@sha256:...`) so a classroom start does not change when upstream tags move. Keep a provenance and license ledger for every binary, image, sample log, and borrowed code asset.
2. Bake Grafana, Loki, Alloy, the target app, test fixtures, configs, and systemd units into the images. Do not run `apt`, download tools, clone Git repositories, fetch third-party roles, or retrieve exercise data at learner startup or during exercises. Artifact publication by the author and platform image retrieval happen outside the guest; validate this path with a private-only guest.
3. Use short `initTasks` only to generate per-instance fixture IDs and a disposable Grafana password, reset local exercise state, start/verify services, and show a clear readiness failure if a service is unhealthy. Store any generated password in a file readable to the learner inside the instance; never embed a shared credential in the manifest or image. Do not put secret material in public startup files, URLs, task output, or reference answers.
4. Configure Alloy to collect narrowly selected journald units and the app log, label by machine/service, and push **only** to the Loki private IP. The Alloy service account needs the documented journal group membership. Provision Grafana's datasource with **only** the private Loki address and a small starter dashboard automatically. Loki has no built-in authentication, so keep its API off any published URL.
5. Disable optional outbound reporting and update checks in all three products: Alloy `--disable-reporting`; Loki `analytics.reporting_enabled: false`; Grafana `[analytics] reporting_enabled = false`, `check_for_updates = false`, and `check_for_plugin_updates = false`. Disable Grafana's automatic plugin installation and plugin public-key retrieval; use only bundled, pinned plugins. Review the selected rootfs for unattended package updates, crash reporting, external time synchronization, or other background network clients. A private network route is the primary egress boundary, but removing these defaults also makes the software's intent explicit.
6. Cap journal and Loki storage, log rate, app request rate, process runtime, and disk use. A scenario supervisor (`lab scenario start|stop|reset|status`) runs one bounded event generator at a time and cleans up on completion or interruption. Startup should never launch a continuous attack generator.

**Fallback if the two-VM log stack exceeds the free-tier budget:** first tune Loki retention, ingestion, and Grafana features; then test a single VM with the same real log sources and query UI. If neither gives a responsive experience, explicitly require a paid tier rather than silently scaling down or substituting pre-recorded logs for every exercise.

## Exercise sequence (about 75–100 minutes)

| Module | Learner action in their own instance | What to observe and check | Safety boundary |
| --- | --- | --- | --- |
| 1. Trace one event (15 min) | Use a documented `curl` request to the known target app address and inspect its `journalctl` output, Alloy status, and Grafana Explore | The same request ID appears at the app and in Loki; learner identifies source, transport, labels, and ingest delay | One known app endpoint, a small number of requests |
| 2. Investigate an access pattern (20 min) | Use seeded fake users to make one normal login, several capped failed logins, and a final successful login to the lab app | Compare successes and failures by session ID/IP; write a query for the bounded pattern; explain why a typo alone should not alert | App-only fake credentials, per-scenario request cap, no SSH brute force or external auth service |
| 3. Correlate host and app activity (20 min) | Run an author-provided script as the unprivileged learner that reads a seeded fictional document, performs `uname`/`ls` in the lab directory, and writes a marker with `logger`; optionally issue one HTTP request to the known app | Correlate app request, service journal, and marker events. If auditd is supported, inspect a narrowly scoped file/process audit event as a stronger host evidence source | Only fake files and own VMs; no credential dump, privileged persistence, exploitation, or external destination |
| 4. Write and test a detection (20–30 min) | Edit a saved LogQL query for the access pattern or host/app correlation, replay the bounded positive case, then replay a benign negative case | Query finds the positive event and does not flag the benign case; learner documents one evasion and one false-positive risk | Query/replay only; no arbitrary Atomic Red Team runner |

An optional fifth lesson can inspect **passive** packets between these two VMs: capture only the lab's private interface for a few seconds while sending one request to a known service, then stop the capture. It should teach request/response and the limits of packet visibility. Do not include host discovery, a port sweep, vulnerability scanning, or packet capture of any iximiuz management or other tenant network. Treat the optional capture as a separate platform compatibility and policy gate.

The teaching page should show a task goal, one or two hints that reveal the next investigative step, a reset button/command, and an explanation after verification. Prefer verification based on **resulting state** (a saved query or a bounded successful replay) over an exact command string. A checker should never run a user-supplied shell command. Where a query answer has several valid forms, accept a short explanation or self-check instead of forcing one exact LogQL expression.

## Explicit exclusions and threat model

Do not transplant the original repository's generic `simulate` endpoint, custom atomic YAML upload, arbitrary Ansible role upload, cloud provisioning, WireGuard share flow, Kali/Windows/AD/Cisco templates, cloud packet mirroring, or public `0.0.0.0/0` access defaults. The original build installs external Galaxy roles and the minimal template downloads a Splunk tarball; neither belongs in the new learner startup. These are architectural exclusions, not hidden switches in the published playground.

The published scenarios must exclude **network and port scanning**, including scans inside the playground under the user's stated iximiuz rule, as well as exploitation of platform services, credential harvesting, malware, C2, phishing, denial-of-service testing, mining, high-volume traffic, and workloads that continue unattended. Local, read-only file matching on seeded lab files (for example, a YARA-X rule) is a separate activity and can be included after resource and content review. A one-port service health check to a known private lab endpoint is qualitatively different from enumerating ports; verify that iximiuz accepts it if the exercise requires one. iximiuz's terms explicitly prohibit large-scale network scanning and 24/7 autonomous workloads and warn against sensitive data in playgrounds. Our exercise rule is the stricter **no network or port scans** rule.

**Limit of enforcement:** a normal iximiuz playground provides a real Linux shell, and the platform says `root` is always available. A curated menu of exercises cannot technically prevent an arbitrary shell user from attempting other commands. Private-only networking, no external route, bounded authored scripts, short instance lifetime, and platform access controls reduce consequences; they do not turn a full shell into a command allowlist or guarantee that a guest cannot be misused. Guest firewall rules and disabled telemetry settings can be changed by a guest root user, so they are not substitutes for the platform's network boundary. If iximiuz requires hard prevention of all unsafe commands, keep the learner in a restricted application interface instead of offering a general terminal, or obtain platform-supported network/process controls before publication. Do not advertise the two-VM design as a security boundary stronger than the platform actually provides.

The intended trust boundary is: **learner controls their disposable guest; learner must not affect iximiuz infrastructure, other learners, or outside networks**. Use fictional data only, no production tokens, no cloud credentials, no SSH agent forwarding, no shared Grafana password, and no public Loki API. Dependency images are trusted supply-chain inputs: pin them, record licenses, and scan/review them during authoring. The team should record an abuse contact and a fast way to unpublish or revoke the template if platform operators report unintended traffic.

## Implementation phases and release gates

1. **Platform agreement and spike.** Confirm with iximiuz that a private-only two-VM lab, local service requests, journald collection, a private Grafana tab, and optional private-interface packet capture are permitted. On a disposable instance, test browser and `labctl` access to VMs with only `private: true` interfaces. Confirm image pulls happen outside the guest, document how browser/CLI access and the Grafana tab are proxied, inspect DNS and routes, and determine whether platform management traffic is visible to or initiated by the guest. If private-only access requires guest public egress, redesign before building the curriculum.
2. **Build the images and manifest.** Add a small dedicated source tree (manifest, Dockerfiles, app, Alloy/Loki/Grafana configs, scenario scripts, content, and license ledger) under a new project directory. Keep this standalone; copy only Apache-2.0-compatible code from `attack_range` if there is a concrete reason, and preserve notices. Bake all runtime dependencies. Use systemd units and health checks rather than Ansible.
3. **Build and observe one event end to end.** Make `target-01` emit a uniquely tagged login/request event; require it to arrive at the private Loki IP, be searchable in Grafana, and disappear when the instance is destroyed. Check that no default service is publicly reachable and no guest service has a configured public destination. This is the minimum technical proof before writing four modules.
4. **Author bounded scenarios and content.** Implement scenario supervisor, positive/negative fixtures, guide, hints, reset behavior, and state-based checks. Keep all targets fixed to the lab's own private addresses and bundle every sample file locally. Include exact expected event fields and a simple troubleshooting path when telemetry is delayed.
5. **Cold-start and misuse review.** Test the final rootfs digests and manifest from a fresh learner account on the intended tier. Record boot time, peak RAM/CPU, disk growth, per-scenario traffic, service recovery after reset, and cleanup after Destroy/expiry. Review every scenario script, image service, collector/exporter config, and browser UI asset for public destinations, unbounded loops, credentials, and accidental public exposure. Verify a full learner pass in browser and via `labctl`. Inspect guest routes and passive traffic/flow evidence for unexpected outbound attempts; do not probe external hosts to perform this check.
6. **Publish and maintain.** Publish only after platform permission, private-network access, resource, telemetry, content, and safety gates pass. Add an update process for pinned images and a repeatable cold-start regression check. Test that each release still fits the target tier and that stale runs are destroyed or expire.

### Required acceptance evidence

- Two fresh instances started by different learners have different VM state, credentials, and data; neither can reach the other's services.
- Both VMs are usable from the browser and `labctl` with only private guest networking, or an approved alternative is documented.
- No guest has a default Internet route; the authored exercises and bundled services have no configured public destinations and send application traffic only to loopback or known endpoints on the playground's private subnet. Verify with route inspection, config review, and passive traffic/flow evidence, **not by contacting or scanning external hosts**.
- Alloy, Loki, and Grafana usage reporting and update checks are disabled; no runtime package/plugin fetches, cloud exporters, external DNS/NTP dependencies, browser-side third-party assets, or public telemetry destinations remain. Any platform-managed control or image traffic is documented separately and accepted by iximiuz.
- The Grafana tab is accessible only to the intended instance owner; Loki and the fixture app are not publicly exposed by default.
- Every exercise yields real, timely events and its positive and negative checks behave as described. If auditd is included, prove its events are actually produced on the selected guest kernel; otherwise omit that evidence source and adjust the lesson.
- Peak memory/CPU and disk use fit the intended tier with margin; scenario timeouts and reset/Destroy remove all activity and data as expected.
- Every image and copied asset has a pinned version/digest and an identified license; no production or sensitive data is present in the images or fixtures.
